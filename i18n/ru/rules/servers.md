# Серверы

Серверы, к которым у harness есть доступ, перечислены в `registry/servers.json`. Список: `bin/harness servers`; проверка входа: `bin/harness server-check [имя]`.

## Откуда настраивается сервер

- Связи «репозиторий → сервер → сервис» записаны в `registry/services.json`. Перед любой работой с сервером или сервисом посмотри их: `bin/harness map <сервер | репозиторий | сервис>`.
- Источник правды для конфигурации — репозиторий из связи. Меняй конфигурацию там и доставляй способом из поля `deploy`; на самом сервере её не правь.
- Если на сервере есть сервис, а связи для него нет, — скажи владельцу и предложи записать её через skill `service-add`.

## Как подключаться

- Только по SSH и только по ключу из окружения владельца (ssh-agent, `~/.ssh/config`). Ключи, пароли и парольные фразы в harness не хранятся, не запрашиваются и не выводятся.
- Всегда неинтерактивно: `ssh -o BatchMode=yes -o ConnectTimeout=10 -p <порт> <user>@<host> '<команда>'`. Без `-A` (проброса агента) и без `-t`, если это не нужно задаче.
- Ключ незнакомого хоста сам не принимай: покажи владельцу отпечаток и дождись подтверждения (это шаг skill `server-add`).
- К серверу, которого нет в реестре, не подключайся — сначала добавь его через `server-add`.

## Что можно делать

- Читать можно свободно: состояние сервисов и контейнеров, логи, метрики, конфигурацию, свободное место.
- Всё, что меняет сервер, — только после подтверждения владельца с перечнем конкретных действий: перезапуск и остановка сервисов и контейнеров, правка конфигурации, установка и обновление пакетов, удаление файлов, изменение правил файрвола, пользователей и ключей, перезагрузка.
- На серверах с `"env": "prod"` дополнительно назови, что именно затронет действие и как его откатить.
- Изменения кода и образов доставляй штатным пайплайном проекта (коммит → тег → деплой), а не ручными командами на сервере. Ручная правка на проде — только как срочная мера по решению владельца, и её нужно сразу же перенести в репозиторий.

## Вывод и секреты

- Ограничивай вывод: `tail -n`, `journalctl -n`, `docker logs --tail`, `grep`. Логи целиком в контекст не тяни.
- Не выводи секреты с сервера: `.env`, приватные ключи, дампы переменных окружения контейнеров (`docker inspect`, `printenv`). Нужно проверить переменную — проверяй наличие, а не значение.
- Ничего с сервера не копируй в репозитории без просьбы владельца.
