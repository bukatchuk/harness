---
name: push
description: Отправить коммиты harness или проекта из repos/ в удалённый репозиторий с проверкой авторства. Использовать, когда владелец просит запушить.
argument-hint: "[проект]"
---

Отправь коммиты. Аргументы: $ARGUMENTS

1. Определи репозиторий (проект из `repos/<имя>` или сам harness) и текущую ветку: `git -C <путь> rev-parse --abbrev-ref HEAD`.
2. Проверь исходящие коммиты: `bin/harness check-commits <путь>`. Если есть `FAIL` — не отправляй, покажи владельцу, что не так, и предложи исправление.
3. Покажи, что уйдёт: `git -C <путь> log --oneline @{u}..HEAD` (если upstream нет — `git log --oneline -10`).
4. Сверься с реестром: если у проекта `"flow": "pr"`, а текущая ветка — основная, не отправляй напрямую. Предложи ветку и PR через skill `pr-create`. Если `flow` не задан (`null`) — спроси владельца, как в этот проект вносятся изменения, и запиши ответ в реестр.
5. Отправь: `git -C <путь> push` (для новой ветки — `git push -u origin <ветка>`). Для harness отправь и тег версии: `git push origin <ветка> v<версия>`; push коммитов без подъёма версии отклонит git-хук.
6. Если push отклонён, потому что удалённая ветка ушла вперёд, — сделай `git pull --rebase` и повтори. `--force` и `--force-with-lease` — только с явного согласия владельца на этот конкретный push.
7. Для harness создай релиз на каждый отправленный тег: `gh release create v<версия> --verify-tag --title "v<версия> — <суть>" --notes "<описание>"`. Описание — на языке владельца, все изменения функционала со ссылками на md-файлы; формат — в `.claude/rules/harness.md`.
8. Сообщи итог: ветка, число отправленных коммитов, ссылка на репозиторий или релиз.
