---
name: repo-remove
description: Удалить репозиторий из реестра harness (registry/repos.json) и, по решению владельца, его клон из repos/. Использовать, когда владелец говорит, что проект больше не ведётся через harness.
argument-hint: "<репозиторий>"
---

Удали репозиторий из реестра. Аргументы: $ARGUMENTS

1. Найди проект в реестре и посмотри состояние клона: `bin/harness status`. Запомни, есть ли изменённые файлы и неотправленные коммиты.
2. Покажи, какие связи на него ссылаются: `bin/harness map <репозиторий>`.
3. Объясни последствия:
   - из реестра удаляется запись; удалённый репозиторий (GitHub, GitLab) не затрагивается;
   - связи, в которых этот репозиторий — источник конфигурации, с флагом `--unlink` удаляются целиком — назови их поимённо;
   - клон в `repos/<имя>` по умолчанию остаётся на диске. Удалить его — отдельное решение владельца.
4. **Спроси согласия и дождись ответа.** Отдельно спроси про клон. Если в клоне есть изменённые файлы или неотправленные коммиты, скажи об этом прямо и назови числа: удаление клона уничтожит эту работу без возможности восстановить.
5. Удали: `bin/harness repo-remove <репозиторий>` с нужными флагами:
   - `--unlink` — удалить и связи этого репозитория; без флага команда откажется, если связи есть;
   - `--delete-clone` — удалить клон; команда откажется, если в нём есть несохранённая работа;
   - `--force` — удалить клон даже с несохранённой работой. Только после явного согласия владельца именно на потерю этой работы.
   Перед изменением команда сохраняет копию реестра в `.harness-backup/`; клоны туда не копируются.
6. Проверь: проекта нет в `bin/harness status`, `bin/harness doctor` не сообщает о битых ссылках.
7. Если `registry/` отслеживается в git этого harness, это изменение harness: при коммите оно поднимает patch-версию.
