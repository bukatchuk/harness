---
name: service-remove
description: Удалить из реестра harness (registry/services.json) связь между репозиторием и сервером. Использовать, когда владелец говорит, что сервис больше не развёрнут или связь записана ошибочно, а также для полного вывода сервиса из эксплуатации (сервер, прокси, DNS, репозиторий).
argument-hint: "<сервис>"
---

Удали связь из реестра. Аргументы: $ARGUMENTS

1. Покажи владельцу, что будет удалено: `bin/harness map <сервис>`. Если имя не найдено — покажи все связи (`bin/harness map`) и уточни.
2. Объясни последствие: удаляется только запись в реестре. Сам сервис на сервере и репозиторий остаются как есть; после удаления harness перестанет знать, откуда этот сервис настраивается.
3. **Спроси согласия и дождись ответа.**
4. Удали: `bin/harness service-remove <сервис>`. Команда перед изменением сохраняет копию реестра в `.harness-backup/`.
5. Проверь: `bin/harness map <сервис>` отвечает, что связей нет; `bin/harness doctor` не сообщает о битых ссылках.
6. Если `registry/` отслеживается в git этого harness, это изменение harness: при коммите оно поднимает patch-версию.

## Полный вывод сервиса из эксплуатации

Если владелец закрывает сервис целиком (сервер, репозиторий, домен), удаление записи — последний шаг. Сначала найди все следы: `bin/harness map <сервис>`, поиск имени и домена по всем клонам (`grep -rIl <домен> repos/`), сервер (контейнеры, каталоги, ключи, сертификаты), трекер задач. Владельцу — план с перечнем действий по шагам; изменяющие шаги — по правилам `.claude/rules/servers.md`, каждый необратимый — с откатом или копией. Соседние сессии, которые пользуются сервисом, предупреди заранее.

Порядок важен — каждый шаг не должен ломать следующий:

1. **Ссылки на сервис** в других проектах (меню и подвалы сайтов, README, примеры) — их штатным порядком выпуска.
2. **Мониторинг** — пробы, цели, алерты, таблицы ключей. До остановки, иначе придут ложные алерты.
3. **Входной прокси** — конфигурация домена. До удаления сертификата: прокси со ссылкой на удалённый сертификат не пройдёт проверку конфигурации.
4. **Сервер:** контейнеры, все образы сервиса (не только текущий тег) и его сеть, каталог развёртывания, ключи выкладки в `authorized_keys` (перед правкой — копия файла), сертификат. Если compose требует переменных, которые задаёт скрипт выкладки, `docker compose down` не сработает — останавливай по имени контейнера и проверяй результат, а не код возврата конвейера команд.
5. **DNS** — запись домена, рост серийного номера зоны; проверка — `NXDOMAIN` у каждого сервера имён.
6. **Репозиторий:** полная копия (`git bundle create <файл> --all`, `git bundle verify`), выгрузка в хранилище копий владельца и сверка контрольной суммы скачанной обратно копии; затем удаление проекта у хостинга кода и его зеркал. GitLab удаляет проект с задержкой (переименовывает в `…-deletion_scheduled-<id>`) — окончательно: повторный `DELETE /projects/<id>` с `permanently_remove=true` и `full_path`. Для удаления на GitHub нужен `gh` с правом `delete_repo`; если его нет — скажи владельцу.
7. **Реестр harness:** `bin/harness service-remove <сервис>`, затем `bin/harness repo-remove <репозиторий> --unlink --delete-clone`; упоминания в `.claude` других проектов; релиз harness.
8. **Задачи** про сервис в трекере — закрыть с комментарием по решению владельца.

После каждого шага проверь, что соседние сервисы на том же сервере отвечают как раньше.
