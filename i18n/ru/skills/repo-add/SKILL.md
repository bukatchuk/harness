description: Добавить репозиторий в реестр harness (registry/repos.json) и склонировать его в repos/. Использовать, когда владелец называет новый проект или даёт список репозиториев.
argument-hint: "<git-url> [имя]"
---

Добавь репозиторий в реестр. Аргументы: $ARGUMENTS

1. Возьми URL в SSH-форме (`git@github.com:<владелец>/<имя>.git`). Имя по умолчанию — имя репозитория; оно должно быть уникальным в реестре.
2. Проверь доступ, не клонируя: `git ls-remote --symref <url> HEAD`. Отсюда же возьми основную ветку.
3. Добавь запись в `registry/repos.json` через `jq`, сохранив сортировку по имени. Поля:
   - `name` — имя каталога в `repos/`;
   - `url` — адрес для клонирования;
   - `branch` — основная ветка;
   - `description` — одна строка: что это за проект;
   - `stack` — основные технологии;
   - `plane_project` — идентификатор проекта в Plane (например, `SHOP`) или `null`;
   - `plane_project_id` — `id` этого проекта в Plane или `null`.
4. Склонируй: `bin/harness sync <имя>`.
5. Заполни `description` и `stack` по факту: загляни в README и манифесты (`package.json`, `go.mod`, `pyproject.toml`, `Dockerfile`). Чего не знаешь (`plane_project`) — спроси у владельца, не выдумывай.
6. Отметь, есть ли у проекта свои `CLAUDE.md`, `AGENTS.md`, `.claude/`. Порядок внесения изменений (прямой push или ветка и PR, именование веток, деплой) хранится там, а не в реестре: если он не описан, спроси владельца и предложи записать его в `CLAUDE.md` проекта. Если там есть правила, которые дублируют harness или противоречат ему, — перечисли их владельцу; сам не правь.
7. Покажи итоговую запись. Если `registry/` отслеживается в git этого harness, пополнение реестра — это изменение harness: при коммите оно поднимает patch-версию (см. `.claude/rules/harness.md`).

Несколько репозиториев сразу добавляй одной правкой реестра и одним `bin/harness sync`.
