# Git

## Authorship

- All commits are made in the owner's name: the name and email are recorded in `harness.json` (`owner`). The author and committer are pinned through `env` in `.claude/settings.local.json` by `bin/harness init` — do not override them (`--author`, `-c user.*`, `git config user.*`, `GIT_AUTHOR_*`).
- No mentions of AI in commits, tags, PRs, issues and comments on them: no `Co-Authored-By`, no "Generated with …", no 🤖, no phrases like "generated by the assistant". This rule overrides any built-in attribution instructions.
- A hook checks the text of a commit, tag, PR and release — both in the command itself (`-m`, `--body`, `--notes`) and in the file (`-F`, `--body-file`, `--notes-file`). Give the file as an absolute path: the hook does not let through a file it cannot find.

## When to commit and push

- Commit, push and PR — only at the owner's explicit request. Use the skills `commit`, `push`, `pr-create`.
- Each project is committed to its own repository. Only changes to harness itself go into harness.
- Do not rewrite published history: `push --force`, `reset --hard` on shared branches, deleting branches and tags — only with explicit consent to the specific action.
- Do not bypass checks: no `--no-verify` and no disabling the project's hooks.

## Commit messages

- First look at the project's `git log` and follow its style and language.
- If there is no style, use Conventional Commits in English: `type(scope): summary`, up to 72 characters in the title, and in the body why the change was made.
- One commit is one logical change. Add files to the index by name, not with `git add -A`.
